1 Basics & Fundamentals

Primitive vs Reference Types interview

Primitive Types
  • byte, short, int, long, float, double, char, boolean
  • Stored directly on the stack
  • Default: 0, false, '\u0000'
Reference Types
  • Objects, arrays, Strings — stored on heap
  • Variable holds a pointer (memory address)
  • Default: null
  • Compare with .equals(), not ==

Wrapper Classes & Autoboxing interview

Each primitive has a wrapper: int→Integer, double→Double, char→Character, etc.

  • Autoboxing — automatic primitive → wrapper (when adding int to List<Integer>)
  • Unboxing — automatic wrapper → primitive
List<Integer> list = new ArrayList<>();
list.add(42);          // autoboxing: int → Integer
int val = list.get(0); // unboxing: Integer → int
Trap: Integer caches -128 to 127. So Integer a=127, b=127; a==b → true, but Integer a=200, b=200; a==b → false! Always use .equals().

Pass by Value interview

Java is always pass-by-value. For objects, the value is the reference (memory address). A method can mutate the object's contents, but it cannot make the caller's variable point to a different object.
void change(int x)       { x = 99; }           // caller's int unchanged
void mutate(List<String> list) { list.add("hi"); } // caller's list IS mutated
void reassign(List<String> list) { list = new ArrayList<>(); } // caller unchanged

Type Casting

  • Widening (automatic) — smaller → larger (int→long→double), safe
  • Narrowing (manual) — larger → smaller, may lose data: (int) myDouble
  • Upcasting — child object → parent reference, always safe
  • Downcasting — parent reference → child type, use instanceof first to avoid ClassCastException
Animal a = new Dog();      // upcasting — safe ✅
if (a instanceof Dog dog)  // Java 16+ pattern matching
    dog.bark();             // downcasting — safe with instanceof check ✅

Variable Naming Rules interview

  • Can start with a letter, _, or $ — cannot start with a digit
  • Case-sensitive, no reserved keywords, unlimited length

Variable Shadowing interview

A local variable with the same name as an instance field hides the field in its scope. Use this.field to access the instance field.

class Foo {
    int x = 10;
    void bar() {
        int x = 20;               // shadows instance x
        System.out.println(x);       // 20 — local
        System.out.println(this.x);  // 10 — instance
    }
}

Initialization Order interview

Order within a single class:

  1. Static fields & static blocks (in declaration order) — once when class loads
  2. Instance fields & instance initializer blocks — every object creation
  3. Constructor body

With inheritance — the full order when creating a child object:

  1. Parent static fields + static blocks (only once, when class first loaded)
  2. Child static fields + static blocks (only once)
  3. Parent instance fields + instance initializer blocks
  4. Parent constructor body
  5. Child instance fields + instance initializer blocks
  6. Child constructor body
class Parent {
    static { System.out.println("Parent static"); }  // 1st
    { System.out.println("Parent instance"); }        // 3rd
    Parent() { System.out.println("Parent constructor"); } // 4th
}
class Child extends Parent {
    static { System.out.println("Child static"); }   // 2nd
    { System.out.println("Child instance"); }         // 5th
    Child() { System.out.println("Child constructor"); } // 6th
}
Multiple static blocks are executed in the order they appear in the file. You can have as many as you want.

Number Systems interview

  • Octal: starts with 0 — 053 = 5×8+3 = 43 decimal
  • Hex: starts with 0x — 0xFF = 255
  • Binary: starts with 0b — 0b1010 = 10

var — Local Type Inference (Java 10+)

The var keyword lets the compiler infer the type of a local variable from context. It is NOT dynamic typing — the type is fixed at compile time.

var list = new ArrayList<String>();  // inferred as ArrayList<String>
var name = "ahmed";                   // inferred as String
var i = 0;                            // inferred as int
  • Only for local variables — NOT for fields, method params, or return types
  • Cannot be initialized to null (compiler can't infer the type)
  • Use when the type is obvious from the right side; avoid when it harms readability

Enums interview

Enums are special classes that represent a fixed set of constants. They are type-safe and can have fields, methods, and constructors.

enum Day {
    MONDAY, TUESDAY, WEDNESDAY, THURSDAY, FRIDAY, SATURDAY, SUNDAY
}

// Enum with fields and methods
enum Planet {
    MERCURY(3.303e+23, 2.4397e6),
    EARTH(5.976e+24, 6.37814e6);

    private final double mass;
    private final double radius;

    Planet(double mass, double radius) {
        this.mass = mass;
        this.radius = radius;
    }

    double surfaceGravity() { return 6.67300E-11 * mass / (radius * radius); }
}
  • Day.values() → returns all constants as an array
  • Day.MONDAY.name() → "MONDAY" (String)
  • Day.MONDAY.ordinal() → 0 (position, 0-indexed)
  • Day.valueOf("MONDAY") → Day.MONDAY
  • Enums implicitly extend java.lang.Enum, so they can't extend another class
  • Enums can implement interfaces
  • EnumSet and EnumMap are optimized collection types for enums
  • Use in switch statements — more readable and type-safe than String/int constants

Arrays interview

  • Array vs ArrayList: Array is fixed-size, can hold primitives, faster. ArrayList is dynamic, only objects, more flexible.
  • Multidimensional arrays: int[][] grid = new int[3][4];
  • Jagged arrays — rows can have different lengths. Declared and filled row by row:
int[][] jagged = new int[3][];
jagged[0] = new int[]{1, 2};         // row 0 has 2 elements
jagged[1] = new int[]{3, 4, 5};     // row 1 has 3 elements
jagged[2] = new int[]{6};           // row 2 has 1 element

// Access: jagged[row][col]
System.out.println(jagged[1][2]);   // 5

Garbage Collection & References

  • Strong reference — never GC'd while reachable
  • Weak reference (WeakReference<T>) — GC can collect even if weakly reachable (good for caches)
  • Soft reference — only collected when JVM is low on memory
  • finalize() is deprecated — use try-with-resources instead

2 Object-Oriented Programming

The 4 Pillars

Encapsulation

Bundle data & behavior together. Hide state with private fields, expose via getters/setters. Protects from invalid state.

Abstraction

Expose only what's necessary — hide implementation details. Done via abstract classes (partial impl) and interfaces (pure contracts).

Inheritance

Child extends parent with extends. Single-inheritance only for classes. All classes implicitly extend Object.

Polymorphism

Compile-time: method overloading (same name, different params). Runtime: overriding (child redefines parent method — dynamic dispatch).

Abstract Class vs Interface interview

Abstract ClassInterface
Can have state (fields)Only constants (public static final)
Can have constructorsNo constructors
Single inheritance onlyA class can implement multiple interfaces
Any access modifiersMembers are public by default
Use when sharing code among related classesUse for unrelated classes to share a contract

Java 8+: interfaces can have default and static methods. Java 9+: private methods too.

Multiple Inheritance & Diamond Problem interview

Java doesn't allow a class to extend multiple classes. If both parents have the same method, the compiler can't decide which behavior to inherit — this is the diamond problem. Interfaces work around it by requiring the implementing class to override the conflicting default method.

Method Overloading vs Overriding interview

OverloadingOverriding
Same class, same name, different parametersChild redefines parent's method with same signature
Resolved at compile-timeResolved at runtime (dynamic dispatch)
Return type can differ freelyReturn type must be same or covariant
Access modifier: anythingCannot reduce parent's access modifier

super and this interview

  • this — current object reference; also calls another constructor: this(args) (must be first statement)
  • super — parent class reference; super(args) calls parent constructor (must be first statement); super.method() calls parent method

Immutable Objects interview

  1. Declare class as final
  2. All fields private final
  3. No setters
  4. Deep-copy mutable fields in constructor and getters

Examples: String, Integer, LocalDate

Shallow vs Deep Copy interview

  • Shallow copy — copies the object, but nested object references still point to the same originals. Changes to nested objects affect both copies.
  • Deep copy — recursively copies everything. Each copy is fully independent.
  • Default Object.clone() is shallow. Override clone() or use serialization for deep copy.

Serialization interview

Converting an object to a byte stream (to save/send) and back. Implement Serializable (marker interface). Define private static final long serialVersionUID for version compatibility. Mark sensitive fields transient to skip them.

Anonymous Inner Classes & Lambda interview

An anonymous inner class implements an interface or extends a class inline, without naming the class. Since Java 8, functional interfaces can replace them with lambdas.

// Anonymous inner class (old way)
Runnable r = new Runnable() {
    public void run() { System.out.println("hi"); }
};

// Lambda (new way — same thing, much shorter)
Runnable r = () -> System.out.println("hi");

Anonymous classes can capture effectively final local variables. They are useful when you need to implement a non-functional interface (more than one method) inline.

Generics & Type Erasure interview

Generics add compile-time type safety. At runtime, type parameters are erased — replaced with Object or the bound. This is type erasure.

  • You can't do new T(), instanceof T, or create T[] at runtime
  • List<String> and List<Integer> are the same type at runtime (List)
  • Wildcards: ? extends T (upper bound — read), ? super T (lower bound — write)

Memory Leaks in Java interview

Java has a GC but memory leaks are still possible when objects are unintentionally kept reachable:

  • Static collections — adding objects to a static Map/List that never get removed
  • Unclosed resources — streams, connections not closed (use try-with-resources)
  • Listeners/callbacks not removed — registered observers never unsubscribed
  • Inner class holding outer reference — non-static inner class always holds a ref to its outer class
  • ThreadLocal not cleaned up — in thread pools, ThreadLocal values survive task boundaries

Annotations interview

Annotations provide metadata about code to the compiler, tools, or runtime. They don't change program logic directly.

  • @Override — tells compiler this method overrides a parent method; catches typos
  • @Deprecated — marks a method/class as outdated; compiler issues a warning
  • @SuppressWarnings — suppresses specific compiler warnings
  • @FunctionalInterface — verifies interface has exactly one abstract method
  • @SafeVarargs — suppress unchecked warnings on varargs methods

Custom annotations are defined with @interface and can have retention policies (SOURCE, CLASS, RUNTIME). Runtime annotations can be read via reflection.

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
public @interface MyAnnotation {
    String value() default "default";
}

Reflection interview

Reflection lets you inspect and manipulate classes, methods, and fields at runtime, even private ones. Used heavily in frameworks (Spring, JUnit, Hibernate).

// 3 ways to get a Class object
Class<?> clazz = String.class;                     // compile-time
Class<?> clazz = obj.getClass();                   // from instance
Class<?> clazz = Class.forName("java.lang.String"); // by name (can throw ClassNotFoundException)

// Inspect
clazz.getName();                     // "java.lang.String"
clazz.getDeclaredFields();           // all fields including private
clazz.getDeclaredMethods();          // all methods
clazz.getSuperclass();               // parent class
clazz.getInterfaces();               // implemented interfaces

// Access a private field
Field f = clazz.getDeclaredField("value");
f.setAccessible(true);               // bypass private restriction
Object val = f.get(instance);        // read
f.set(instance, newValue);          // write

// Invoke a method dynamically
Method m = clazz.getDeclaredMethod("myMethod", String.class);
m.setAccessible(true);
m.invoke(instance, "argument");      // calls instance.myMethod("argument")

// Create an instance
Constructor<?> c = clazz.getDeclaredConstructor();
Object obj = c.newInstance();
  • Reflection breaks encapsulation — use only when necessary (frameworks, tools)
  • Slower than direct calls — avoid in performance-critical loops
  • Spring uses reflection to wire beans; JUnit uses it to discover test methods

3 Strings

Immutability interview

Strings are immutable — every "modification" creates a new String object. Original is unchanged. Why: thread safety, security (used in class loading & network), enables the String Pool.

String Pool & intern() interview

String a = "hello";        // goes to pool
String b = "hello";        // reused from pool
String c = new String("hello"); // new heap object (NOT pool)

a == b        // true  — same pool reference
a == c        // false — different object
a.equals(c)   // true  — same content ✅

Call c.intern() to put a heap string into the pool and get the pooled reference back.

Always use .equals() for String comparison. Never == — you'll get burned by the pool.

Set & Queue

  • HashSet — no order, O(1), one null allowed. Backed by HashMap.
  • LinkedHashSet — maintains insertion order
  • TreeSet — sorted (uses Comparable/Comparator), O(log n), no nulls
  • EnumSet — optimized for enum values, very fast, backed by bit vector
  • PriorityQueue — min-heap by default, ordered by natural order or Comparator
  • ArrayDeque — double-ended queue, faster than Stack/LinkedList for most uses. Stack is deprecated — use Deque.

equals() and hashCode() Contract interview

Rule: If a.equals(b) == true then a.hashCode() == b.hashCode() MUST also be true.
Same hashCode ≠ equal (that's a collision — allowed). Always override BOTH together.
Breaking this contract silently breaks HashMap/HashSet — objects become impossible to find.

5 Exception Handling

Hierarchy interview

Throwable ├── Error (unchecked — JVM level, don't catch) │ ├── OutOfMemoryError │ └── StackOverflowError └── Exception ├── RuntimeException (unchecked — compiler doesn't force handling) │ ├── NullPointerException │ ├── ClassCastException │ └── ArrayIndexOutOfBoundsException └── (all other checked exceptions) ├── IOException └── SQLException

Checked vs Unchecked interview

CheckedUnchecked
Compiler forces try-catch or throws declarationCompiler does not force handling
Exception subclasses (not RuntimeException)RuntimeException subclasses
Recoverable: file not found, network timeoutProgramming bugs: null pointer, bad argument

try-catch-finally Rules interview

  • finally always runs — even with a return in try
  • If both try and finally have return — finally's return wins, try's is silently discarded
  • finally does NOT run on: System.exit(), JVM crash, infinite loop in try
  • Nothing (not even variable declarations) between try, catch, finally — compile error
  • More specific exceptions MUST come before general — otherwise "unreachable code" compile error
  • Multi-catch: catch (IOException | SQLException e)
  • Duplicate exception in same catch = compile error
  • Errors are NOT caught by catch (Exception e) — need catch (Throwable t)

throw vs throws interview

  • throw — throws the actual exception object: throw new IllegalArgumentException("bad");
  • throws — method signature declaration: public void read() throws IOException

Try-with-Resources interview

Auto-closes any AutoCloseable resource after the block, even if an exception occurs. Replaces old try-finally close patterns.

try (BufferedReader br = new BufferedReader(new FileReader("file.txt"))) {
    System.out.println(br.readLine());
} // br closed automatically ✅

Exception Propagation

When an exception is thrown, JVM searches call stack upward for a matching catch. If none found — default handler terminates the program and prints the stack trace.

Overriding & Exceptions interview

  • Parent throws checked → child can: throw same, throw subclass, or throw nothing. Cannot throw a broader checked exception.
  • Parent throws unchecked → child can do anything

Custom Exceptions

// Checked
class InsufficientFundsException extends Exception {
    InsufficientFundsException(String msg) { super(msg); }
}
// Unchecked
class InvalidOrderException extends RuntimeException {
    InvalidOrderException(String msg) { super(msg); }
}

Streams interview

A lazy, functional pipeline to process data — sequential or parallel. Used once and then consumed.

List<String> result = names.stream()
    .filter(n -> n.startsWith("A"))    // intermediate (lazy)
    .map(String::toUpperCase)           // intermediate (lazy)
    .sorted()                           // intermediate (lazy)
    .collect(Collectors.toList());      // terminal — triggers execution
Intermediate (lazy)
filter(), map(), flatMap(), sorted(), distinct(), limit(n), skip(n), peek()
Terminal (eager — triggers pipeline)
collect(), forEach(), reduce(), count(), findFirst(), anyMatch(), allMatch(), min(), max()
  • Stream functional interfaces: Predicate → filter, Function → map, Consumer → forEach, BinaryOperator → reduce
  • Use .parallelStream() for parallel processing (uses ForkJoin common pool)

Optional<T> interview

A container object that may or may not contain a non-null value. Designed to avoid NullPointerException and make the possibility of absence explicit in the API design.

Optional<String> opt = Optional.of("hello");     // contains value
Optional<String> empty = Optional.empty();        // no value
Optional<String> nullable = Optional.ofNullable(getValue()); // may be null

opt.isPresent()          // true
opt.isEmpty()            // false (Java 11+)
opt.get()                // "hello" (throws if empty — avoid this)
opt.orElse("default")   // returns value or default
opt.orElseGet(() -> computeDefault())  // lazy fallback
opt.orElseThrow(() -> new RuntimeException("not found"))
opt.map(String::toUpperCase)   // Optional<String> "HELLO"
opt.filter(s -> s.length() > 3) // Optional with value only if test passes
opt.ifPresent(System.out::println) // runs if value present
Use Optional as return type of methods that might not have a result. Don't use it for fields or method parameters.

Buffering — Why It Matters

Reading directly from FileReader makes an OS call per character — very expensive. Wrapping in BufferedReader reads a large chunk into RAM and serves reads from the buffer — much faster in most cases.

// wrap the source in a buffer — best practice
BufferedReader br = new BufferedReader(new FileReader("file.txt"));

Java NIO (New I/O)

  • Alternative to traditional I/O — uses Buffers and Channels instead of streams
  • Channel — like a stream but bidirectional (read AND write)
  • Supports non-blocking operations — essential for high-throughput servers
  • Key classes: ByteBuffer, FileChannel, SocketChannel, Selector

8 Multithreading & Concurrency

Process vs Thread

  • Process — running instance of a program; has its own memory space
  • Thread — smallest unit of execution inside a process; threads share the heap but each has its own stack

Creating Threads interview

// 1. Extend Thread
class MyThread extends Thread { public void run() { ... } }
new MyThread().start();

// 2. Implement Runnable (preferred — keeps class hierarchy free)
Thread t = new Thread(() -> System.out.println("running"));
t.start();

// 3. Callable — returns a value, can throw checked exceptions
// Must use ExecutorService, not Thread directly
Future<Integer> f = executor.submit(() -> computeResult());
run() runs on the SAME thread. start() spawns a NEW thread then calls run() inside it. Runnable and Callable are functional interfaces so lambdas work directly.

Thread Attributes & States

States: NEW → RUNNABLE → BLOCKED / WAITING / TIMED_WAITING → TERMINATED

  • priority: MIN=1, NORM=5, MAX=10 — just a hint, not guaranteed
  • Daemon thread — automatically killed when all non-daemon threads finish

Synchronization Tools interview

volatile

Guarantees visibility only — reads directly from main memory, not CPU cache. Does NOT guarantee atomicity. Use for simple flags.

synchronized keyword

Monitor lock. Each synchronized block/method acquires the object's lock (or class lock for static). Automatically releases on exit. Simplest way to synchronize.

ReentrantLock

Like synchronized but with more power: manual lock()/unlock(), fair mode (FIFO), tryLock(), and Condition support. Can lock multiple times from same thread without deadlocking itself (re-entrant).

Condition — tied to a ReentrantLock; await()/signal() for specific conditions. More precise than wait/notify because signal() only wakes threads on that specific condition.

Atomic Classes

Lock-free, CPU-level CAS operations: AtomicInteger, AtomicLong, AtomicReference. Best for counters and simple shared flags.

Other Synchronizers
  • ReadWriteLock — multiple readers OR one exclusive writer at a time; useful when reads are frequent and writes are rare
  • Semaphore — allows at most N threads at a time; acquire() / release()
  • CountDownLatch — threads wait until count reaches zero; one-time use (e.g. wait for N microservices to start)
  • CyclicBarrier — group of threads wait for each other at a meeting point; reusable (e.g. parallel chunk processing that must merge)
  • Exchanger — two threads exchange data at a synchronization point
  • ThreadLocal — per-thread variable; each thread gets its own isolated copy

Thread Pool & Executor Framework interview

Instead of creating a new thread per task (expensive: ~1–2ms + 1MB stack), keep a pool of ready threads.

Executor (interface) └── ExecutorService (interface) └── AbstractExecutorService └── ThreadPoolExecutor ← real engine behind everything └── ScheduledThreadPoolExecutor

  • execute(Runnable) — fire and forget, no feedback
  • submit(Callable) — returns Future<T>

Virtual Threads (Java 21+)

When a virtual thread blocks (I/O, sleep), its state (TCB) is saved in heap memory and the OS thread picks up another virtual thread. This allows handling millions of concurrent tasks with a small number of OS threads.

Best for I/O-bound work. Spring Boot 3.2+: spring.threads.virtual.enabled=true to enable globally.

Future, FutureTask, & CompletableFuture interview

Future problems: get() blocks, no chaining, no combining multiple futures, ugly error handling. CompletableFuture solves all of this.

    .thenAccept(System.out::println);                // consume the result

Fork/Join Framework

Designed for CPU-bound recursive divide-and-conquer. Uses work-stealing: each thread has its own deque; idle threads steal tasks from the back of busy threads' deques — minimizes contention.

// your own pool
ForkJoinPool pool = new ForkJoinPool(4);
Long result = pool.invoke(myTask);

// or the shared common pool (simpler)
Long result = ForkJoinPool.commonPool().invoke(myTask);
CompletableFuture.supplyAsync() uses ForkJoin common pool by default.

Deadlock, Race Condition & Others interview

  • Race condition — two threads access shared mutable data concurrently; outcome depends on timing
  • Deadlock — Thread A holds lock 1 & waits for lock 2; Thread B holds lock 2 & waits for lock 1 — both blocked forever
  • Starvation — a thread never gets CPU time because higher-priority threads always run first
  • Livelock — threads keep reacting to each other but neither makes actual progress

  • Subqueries — a query nested inside another query

11 SOLID Principles

S — Single Responsibility Principle

One class = one reason to change. Ask: "How many reasons do I have to change this class?" If more than one → split it.

❌ User class handles user data AND sends emails → ✅ User + EmailService

O — Open/Closed Principle

Open for extension, closed for modification. Multiple if/else or switch checking types → violation. New behavior = add a new class, don't touch existing code.

❌ if type=="circle"... if type=="square" → ✅ Shape interface → Circle implements, Square implements

L — Liskov Substitution Principle interview

Subclasses must be fully replaceable by their parent without breaking the program. Violated when a child inherits a method it can't meaningfully implement.

❌ Bird → fly() but Penguin extends Bird can't fly → ✅ Split into FlyableBird and base Bird

"If swapping child for parent breaks behavior → LSP violated." — Breaking ISP usually leads to breaking LSP too.

I — Interface Segregation Principle

Don't force classes to implement methods they don't need. Fat interfaces = violation. Break into thin, focused interfaces.

❌ Animal with eat(), fly(), swim() → ✅ Eatable, Flyable, Swimmable — let classes implement only what they need

D — Dependency Inversion Principle

High-level modules should not depend on low-level modules. Both should depend on abstractions. Never reference a concrete class directly — use an interface.

❌ UserService creates EmailService internally → ✅ UserService(NotificationSender sender) — inject the interface

Tomorrow swap to SMSService → UserService never changes! Two ways: constructor injection or method parameter injection.

12 Design Patterns

Common solutions engineers reached after facing the same problems repeatedly — best practices for recurring scenarios.

Creational

How objects are created. Singleton, Builder, Prototype, Factory, Abstract Factory.

Structural

How classes/objects are composed into bigger structures. Adapter, Facade, Proxy, Decorator.

Behavioral

How objects communicate and behave with each other. Chain of Responsibility, Observer, Strategy, Command, etc.

Singleton — Creational

One instance only across the entire application. Thread-safe version uses double-checked locking:

private static volatile Singleton instance;

public static Singleton getInstance() {
    if (instance == null) {                  // first check — no lock (performance)
        synchronized (Singleton.class) {
            if (instance == null) {          // second check — handles race condition
                instance = new Singleton();
            }
        }
    }
    return instance;
}
  • First check: avoids acquiring the lock every call (performance)
  • Second check: in case two threads both passed the first check simultaneously
  • volatile: ensures threads don't read a stale cached value / partially constructed object
  • Examples: DB connection pool, config manager, logger

Builder — Creational

For objects with many constructor parameters. Makes creation readable and self-documenting.

// ❌ Without builder — confusing, what is "true"? what order?
new User("ahmed", 25, "cairo", "ahmed@gmail.com", true, "admin");

// ✅ With builder — clear and readable
User user = new User.Builder()
    .name("ahmed").age(25).city("cairo")
    .email("ahmed@gmail.com").isActive(true).role("admin")
    .build();

Prototype — Creational

Copy an existing object instead of creating from scratch when object creation is expensive. Implement Cloneable and override clone().

  • Shallow copy — copies primitive values and references (nested objects still shared)
  • Deep copy — recursively copies nested objects too; fully independent

Factory & Abstract Factory — Creational

Factory — separates "which class to create" from the caller. Caller requests a type → factory decides and returns via interface → caller never knows the concrete class.

// ❌ messy caller
if (type.equals("dog")) new Dog();
else if (type.equals("cat")) new Cat();

// ✅ clean caller
Animal animal = AnimalFactory.create("dog");

Abstract Factory — factory of factories. For families of related objects that must go together.

FactoryAbstract Factory
One product; if/else returns an objectFamilies of products; if/else returns a factory
Ex: AnimalFactory creates Dog or CatEx: DarkFactory creates DarkButton + DarkTextBox + DarkCheckbox

Structural Patterns — Quick Comparison interview

// Decorator — Java IO is the classic real-world example
new BufferedReader(new FileReader("file.txt"));
// BufferedReader decorates FileReader — adds buffering on top

// Stacking decorators
Pizza p = new PlainPizza();
p = new ChocolateDecorator(p);    // + chocolate
p = new CheeseDecorator(p);       // + cheese on top of that
p.getPrice(); // sums all layers automatically ✅

Chain of Responsibility — Behavioral

Request passes through a chain of handlers. Each handler checks its condition — if OK, passes to next; if not, stops the chain. No handler knows the full chain.

// Build the chain
employee.setNext(manager);
manager.setNext(finance);
finance.setNext(borrowHandler);

// Start it
employee.handle(request);

Real world: Servlet Filters, Spring Security filter chain, logging levels (DEBUG→INFO→WARN→ERROR), Express.js middleware (next()).

Observer — Behavioral

One subject/topic → many subscribers. When something happens, all subscribers are notified automatically. Subscribers are fully decoupled from each other.

Topic topic = new Topic();
topic.subscribe(new EmailSubscriber());
topic.subscribe(new SMSSubscriber());
topic.notify("order placed"); // both get notified ✅

Real world: Java EventListener, Kafka topics + consumers, Spring @EventListener, React state changes notifying components.

🔴 Interview Gotchas & Tricky Topics

These are the most commonly failed topics in Java interviews. Study these carefully.
1. Exception catching order

More specific exceptions MUST come before general ones. If Exception comes before IOException → compiler says "unreachable code". Error is NOT caught by catch(Exception e) — you need catch(Throwable t). Duplicate exception types in the same catch = compile error.

2. finally with return

If both try and finally have a return statement, finally's return wins — the try's return is silently discarded. Very sneaky exam question.

3. String == vs .equals()

== compares references. .equals() compares content. "hello" == "hello" may be true (pool), but new String("hello") == "hello" is always false. Always use .equals() for strings.

4. Pass-by-value with objects

Java is always pass-by-value. For objects, the value passed is the reference (pointer). The method CAN mutate the object's internal state, but it CANNOT make the caller's variable point to a different object. Reassignment inside the method doesn't affect the original.

5. Diamond problem & multiple inheritance

Java classes can't extend multiple classes — if both parents have the same method, the compiler can't choose. Interfaces solve this because the implementing class must explicitly override the conflicting default method.

6. equals() + hashCode() contract

If equals() says two objects are equal, they MUST have the same hashCode. HashMap uses hashCode to find the bucket first, then equals to find the exact key. Overriding only equals silently breaks all collections that use hashing.

7. Integer cache trap (autoboxing)

Integer caches values from -128 to 127. Integer a=127; Integer b=127; a==b → true. But Integer a=200; Integer b=200; a==b → false. Always use .equals() for Integer comparison.

8. String immutability in loops

String concatenation in a loop (s = s + x) creates a new String object every iteration — O(n) objects for n iterations. Always use StringBuilder in loops.

9. volatile in Singleton

Without volatile, a thread can see a partially constructed Singleton object due to CPU instruction reordering. volatile guarantees visibility and prevents reordering — required for correct double-checked locking.

10. ConcurrentModificationException

Modifying a collection while iterating it with a regular for-each throws this exception. Fix: use Iterator.remove() during iteration, collect items to remove and remove after the loop, or use a fail-safe collection (CopyOnWriteArrayList).

11. sleep() vs wait()

sleep() pauses the thread but keeps the lock. wait() pauses the thread AND releases the lock, allowing other threads to enter the synchronized block. wait() must be called from inside a synchronized block.

12. Variable shadowing

A local variable with the same name as an instance field shadows the field in its scope. Easy source of subtle bugs. Use this.field to access the instance field explicitly.

13. Octal literal trap

In Java, a number starting with 0 is octal (base 8). 053 = 5×8 + 3 = 43 in decimal. Common trick question in written exams.

14. Checked exceptions and overriding

An overriding method cannot throw a broader checked exception than the parent. If parent throws IOException, child can't throw Exception. Child can throw a subclass of IOException, or throw nothing. No restriction on unchecked exceptions.

15. abstract class vs interface — when to use which

Use an abstract class when related classes share code and state. Use an interface when you need a contract that unrelated classes can fulfill — and when you need multiple inheritance of type. Java allows implementing multiple interfaces but extending only one class.

16. Static block order with inheritance

When you create a child object, the execution order is always:
1. Parent static blocks → 2. Child static blocks → 3. Parent instance blocks → 4. Parent constructor → 5. Child instance blocks → 6. Child constructor.
Static blocks run only ONCE (when the class is first loaded), never again. Multiple static blocks in the same class run top-to-bottom.

// Output of: new Child();
// "Parent static"  ← always first
// "Child static"   ← always second
// "Parent instance" + "Parent constructor"
// "Child instance"  + "Child constructor"
17. Calling an overridden method from a parent constructor ✔️ Dangerous

If a parent constructor calls a method that is overridden in the child, the child's version runs BEFORE the child's constructor finishes. The child's fields are not yet initialized — they still hold default values (0, null). This is one of the most subtle Java bugs.

class Parent {
    Parent() { print(); }     // calls child's print()
    void print() { System.out.println("Parent"); }
}
class Child extends Parent {
    String name = "ahmed";    // NOT YET set when Parent() runs!
    void print() { System.out.println(name); } // prints null !
}
18. Static methods — hiding, not overriding

Static methods cannot be overridden — they can only be hidden. If a child defines a static method with the same signature, it hides the parent's. Which one runs depends on the reference type at compile time, not the actual object type.

class Parent { static void greet() { System.out.println("Parent"); } }
class Child extends Parent { static void greet() { System.out.println("Child"); } }

Parent obj = new Child();
obj.greet();  // prints "Parent" !! (not Child — no polymorphism for static)
19. Constructor chaining rules
  • this() — calls another constructor in the same class. Must be the first statement in the constructor.
  • super() — calls a constructor in the parent class. Also must be the first statement.
  • You cannot use both this() and super() in the same constructor — compile error.
  • If you don't write super(), Java inserts a call to super() (no-arg) automatically. If the parent has no no-arg constructor, you must call super(args) explicitly — otherwise compile error.
20. try-catch compiler rules summary
  • Nothing (even a comment or variable declaration) allowed between try, catch, and finally blocks — compile error
  • Specific exception MUST come before general: IOException before Exception — otherwise "unreachable catch" compile error
  • Duplicate exception type in same catch block — compile error
  • Error is NOT a subclass of Exception — only caught by catch(Throwable t)
  • Catch without try — compile error. Finally without try — compile error.
  • A try block can have: try+catch, try+finally, or try+catch+finally. try alone — compile error.
21. Illegal modifier combinations — compile errors interview
CombinationWhy Illegal
final abstract class/methodfinal = cannot be extended/overridden; abstract = MUST be extended/overridden. Direct contradiction.
private abstract methodabstract method must be overridden by a subclass, but private = inaccessible to subclass. Contradiction.
static abstract methodabstract requires an instance to override; static belongs to class. Contradiction.
private protected or public privateTwo access modifiers on the same member — always illegal.
volatile final fieldvolatile = can change anytime (bypass cache); final = cannot change. Contradiction.
native abstract methodnative has an external (C/C++) implementation; abstract has NO implementation. Contradiction.
synchronized abstract methodsynchronized needs a method body to lock; abstract has no body. Contradiction.
Easy rule: if two modifiers logically contradict each other, they're illegal together. final+abstract is the #1 most tested pair.
22. Modifiers that constructors CANNOT have

Constructors can only have access modifiers (public, private, protected, or package-private). These are ALL illegal on a constructor:

  • final — compile error (constructors are not inherited so final is meaningless)
  • static — compile error (constructors need an instance)
  • abstract — compile error (abstract must have no body; constructor must have a body)
  • synchronized — compile error
  • native — compile error
  • strictfp — compile error

24. abstract method rules
  • Abstract method has NO body — just a signature ending in ;
  • If a class has even ONE abstract method → the class MUST be declared abstract
  • An abstract class can have zero abstract methods (just prevents instantiation)
  • Abstract class CANNOT be instantiated directly with new
  • A subclass of an abstract class MUST implement ALL abstract methods, or it must also be declared abstract
  • Interface methods are implicitly public abstract (pre-Java 8) unless default or static
25. interface modifier rules
  • Interface itself is implicitly abstract — no need to write it
  • Interface fields are implicitly public static final — always constants
  • Pre-Java 8: all methods implicitly public abstract
  • Java 8+: can have default methods (with body) and static methods
  • Java 9+: can have private methods (helper methods for default/static)
  • Cannot declare an interface method as protected or private (pre-Java 9) — compile error
  • Interface cannot be final — it must be implementable
