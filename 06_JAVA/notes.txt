SOLID

S - Single Responsibility
one class = one reason to change
ask: "how many reasons do i have to change this class?"
if more than one → split it
ex: User class handling both user data AND sending emails → split into
    User + EmailService

O - Open Closed
open for extension, closed for modification
when you see multiple if/else or switch checking types → violation
solution: use abstraction (interfaces) + factory pattern
new behavior → add new class, don't touch existing code
ex: instead of if shape == circle / if shape == square
    make Shape interface → Circle implements, Square implements

L - Liskov Substitution
subclass must be fully replaceable by their parent
violated when child inherits method it doesn't want or can't implement
ex: Bird → fly() but Penguin extends Bird and can't fly → violation
solutions:
  → split parent into smaller interfaces (Interface Segregation!)
  → use composition instead of inheritance
  "if it breaks when you swap child for parent → LSP violated"

I - Interface Segregation
don't force classes to implement methods they don't need
fat interface with many methods → violation
solution: make thin focused interfaces each with one responsibility
ex: don't have Animal with eat(),fly(),swim()
    instead → Eatable, Flyable, Swimmable
    class Duck implements Eatable, Flyable, Swimmable
    class Penguin implements Eatable, Swimmable (no fly!)
breaking ISP usually leads to breaking LSP too

D - Dependency Inversion
high level modules should not depend on low level modules
both should depend on abstraction
never use concrete class reference directly → use interface
two ways to apply:
  → dependency injection: receive interface in constructor
    ex: UserService(NotificationSender sender) not (EmailService sender)
  → method parameters: take interface not concrete class
ex: 
  ❌ UserService directly creates EmailService inside
  ✅ UserService receives NotificationSender interface
     EmailService implements NotificationSender
     tomorrow swap to SMSService → UserService never changes!
     Design Patterns
common solutions engineers reached after facing the same problems
repeatedly and trying different solutions — best practices for
recurring scenarios

Singleton
one instance only of a class across the entire app
how:
  → private constructor (no one can call new)
  → private static instance variable of same type
  → public static getInstance() method
thread safe version → double checked locking:

private static volatile Instance instance; // volatile for visibility!

public static Instance getInstance() {
    if (instance == null) {                    // first check (no lock)
        synchronized (Instance.class) {
            if (instance == null) {            // second check (with lock)
                instance = new Instance();
            }
        }
    }
    return instance;
}

why double check?
  first check  → avoid locking every time (performance)
  second check → in case two threads passed first check simultaneously
why volatile?
  → forces visibility so threads don't read stale cached value

Adapter

implementation:
  → create Adapter class
  → implements YOUR expected interface
  → takes OLD service as composition (constructor injection)
  → inside the method → call old service, convert/wrap result, return it

    but our system expects PaymentResult

class PaymentAdapter implements PaymentResult {
    private OldPaymentService oldService; // composition

    PaymentAdapter(OldPaymentService oldService) {
        this.oldService = oldService;
    }

    public PaymentResult pay(amount) {
        PaymentResponse res = oldService.makePayment(amount); // old way
        return convert(res); // adapt to new format
    }
}

caller never knows about OldPaymentService → only sees PaymentResult ✅
think of it like a power plug adapter — same electricity, different shape

Facade
simplifies a complex set of operations behind one clean interface
used when an operation requires calling multiple services in steps

class PlaceOrderFacade {

        order.create(o);               // step 3
    }
}

  adapter   → converts incompatible interface

Proxy
controls and restricts access to another object
sits exactly in the middle between caller and real object
used for: logging, caching, access control, lazy loading

implementation:
  → both Proxy AND real object implement same interface
  → Proxy takes real object as composition
  → Proxy intercepts the call → does its work → forwards to real object

ex: CachingProxy
class UserServiceProxy implements UserService {
    private UserService realService;        // composition
    private Map<Integer, User> cache = new HashMap<>();

    public User getUser(int id) {
        if (cache.containsKey(id)) {
            return cache.get(id);           // return from cache ✅
        }
        User user = realService.getUser(id); // forward to real service
        cache.put(id, user);                 // cache for next time
        return user;
    }
}

caller uses UserService interface → never knows its a proxy ✅

difference from facade:
  facade → wraps MULTIPLE services into one
  proxy  → wraps ONE service to control access to it

Decorator
adds new behavior to objects dynamically without changing their class
used when subclass hierarchy would get huge due to many combinations

problem without decorator:
Pizza → CheesePizza, PepperoniPizza, ChocolatePizza

  → base interface/class (Pizza)

    }

    public String getDescription() {
        return pizza.getDescription() + " + chocolate";
    }
}

// usage — wrap and stack decorators!
Pizza pizza = new PlainPizza();
pizza = new ChocolateDecorator(pizza);   // plain + chocolate
pizza = new CheeseDecorator(pizza);      // plain + chocolate + cheese
pizza = new PepperoniDecorator(pizza);   // plain + chocolate + cheese + pepperoni

pizza.getPrice(); // sums everything up automatically ✅

Chain of Responsibility
request passes through a chain of handlers
each handler checks its part → if ok passes to next → if not stops chain
no handler needs to know the full chain → only knows its next

implementation:
  → each handler has reference to next handler
  → each handler implements same interface/abstract class
  → handle() method → do your check → if pass call next.handle()
  → chain is built by linking handlers together

ex: borrow a book
class EmployeeHandler implements Handler {
    private Handler next;              // reference to next in chain

    public void setNext(Handler next) {
        this.next = next;
    }

    public void handle(Request req) {
        if (req.hasValidID()) {
            next.handle(req);          // pass to next ✅
        } else {
            System.out.println("Invalid ID - rejected"); // stop chain ❌
        }
    }
}

// build the chain
Handler employee = new EmployeeHandler();
Handler manager  = new ManagerHandler();
Handler finance  = new FinanceHandler();
Handler borrow   = new BorrowHandler();

employee.setNext(manager);
manager.setNext(finance);
finance.setNext(borrow);

// start the chain
employee.handle(request);

real world ex:
  → Java Servlet Filters (each filter passes to next)
  → Spring Security filter chain
  → logging levels (DEBUG → INFO → WARN → ERROR)
  → middleware in Express (next() = pass to next handler!)

ex:
class Topic implements Subject {
    private List<Observer> subscribers = new ArrayList<>();

    public void subscribe(Observer o)   { subscribers.add(o); }
    public void unsubscribe(Observer o) { subscribers.remove(o); }

    public void notify(String event) {
        for (Observer o : subscribers) {
            o.update(event);           // notify all ✅
        }
    }
}

class EmailSubscriber implements Observer {
    public void update(String event) {
        System.out.println("sending email for: " + event);
    }
}

// usage
Topic topic = new Topic();
topic.subscribe(new EmailSubscriber());
topic.subscribe(new SMSSubscriber());

topic.notify("new order placed");
// EmailSubscriber notified ✅
// SMSSubscriber notified ✅

real world ex:
  → Java EventListener
  → message queues (Kafka topics + consumers)
  → Spring @EventListener
  → frontend frameworks (React state changes notify components)

---

Key Implementation Summary

Chain of Responsibility
  → each handler holds reference to next
  → handle() → check → pass or stop
  → chain built by linking handlers
  → caller only calls first in chain

Observer
  → subject holds list of observers
  → subscribe/unsubscribe to manage list
  → notify() loops and calls update() on all
  → observers are decoupled from each other

---

Common Thread
both decouple the sender from receiver ✅
chain  → one request, passes through many handlers sequentially
observer → one event, notifies many subscribers simultaneously
